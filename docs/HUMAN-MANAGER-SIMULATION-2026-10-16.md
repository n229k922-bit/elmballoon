会社PCのCodex作業を自宅PCで引き継ぎ、**架空の顧客役AI → 注文担当AI → 統括AI → 人間の店長役（本人または実店舗の店長） → AI顧客への最終回答**を通しで検証する。人間はテキスト入力で判断する。GitHubへのこの文書保存は仕様と再開手順の追加であり、対話型シミュレーターの実装・動作確認・デプロイが完了したことを意味しない。

## 自宅PCでの再開手順（5ステップ）
1. GitHubとCodexにログイン。ローカルの未保存変更を調べ、上書きしない。リポジトリを初回はcloneし、既存cloneの場合は変更を確認してからfetchする。
2. `codex/production-readiness-20261015` に切り替えてリモートの最新版を取得する。**mainでは開発しない**。
3. `docs/HANDOFF-2026-10-16.md` と本書を読む。Node.js 24（node:sqlite利用）、依存関係、テスト実行方法を確認する。
4. 秘密値・Cloudflare/LINEへのログインはGitにないので、自宅側で必要な権限とテスト設定のみ確認。シークレット、トークン、顧客個人情報はコミットしない。
5. **オフライン・模擬送信・架空顧客のみ**でテスト開始。実LINE接続、本番DB更新、Webhook切替、実顧客への送信は別の明示許可と安全確認が必要。

## 4役の責任分離
- **顧客役AI**：個別の架空ペルソナの希望を保持して発言。注文変更・別注文・キャンセル・返金相談・葬儀・緊急などを扱う。店長役の正解・システム内部情報は渡さない。
- **注文担当AI**：顧客メッセージを実装済み受付コードへ入力し、その**実コードの応答・記録値**を取得する。AIが考案した理想返信でコードの応答を置き換えない。
- **統括AI**：実コードで生成された注文カルテ・不足情報・判断要求・例外/緊急度を整理し、人間店長へ提示。人が指示していない受注・価格・納期・返金を確定しない。
- **人間店長役**：本人または店長がテキストで「承認・保留・差し戻し・追加質問・見送り・変更」を入力。案件番号・版・根拠を固定して反映し、結果を顧客役へ戻す。判断に迷うときは確認を求められる。実店舗の確定ルールとテスト用の架空条件は混同しない。

監査役AIは四役の外側で、会話の自然さと危険な誤処理を評価する。修正担当Codexは別に動かし、監査に合格したという自己申告だけで合格にしない。

## 実装すべき人間参加型の検証ループ
1. テストケースを選ぶ。顧客役にのみ裏設定を与え、人間店長には要約・判断材料と必要なボタンまたは文字入力欄を見せる。
2. 実コードの受付処理と統括処理をローカルの隔離DB/モック通信で実行。送信・承認・カルテ更新の前後状態を保存する。
3. **人間の入力待ちで停止し、勝手に代理承認しない。** 入力後は対象案件と版を検証してから模擬反映する。複数人が参加する場合は誰が判断したかを明記する。
4. 顧客役の追加発言、実コードの返信案、送信可否、店長判断、監査結果を時系列で残す。AIによる創作とコード実行ログを別ラベルで保存する。
5. 同じ入力と初期状態で再現可能な自動テストを追加し、修正前後比較を保存。重大不具合がゼロか、実機で再現するかを別判定する。

## 最初に優先する回帰ケース（既知の不合格）
1. 苦情・キャンセル・返金相談後の単なる「ありがとう」で、通常質問へ戻らず人の確認待ちを維持できるか。
2. 「今日もありがとうございます」の「今日」を受取日として誤記録しないか。日付変更では旧日付と新時刻を混ぜないか。
3. 「前のブーケはそのまま、別件でスタンド1台」で旧注文の数量が汚染されないか。曖昧なら更新保留にするか。
4. 24件の通常相談の後に緊急相談が来ても、初回処理枠から漏れないか。
追加で、弔事の初回文面、否定色、見送り、旧承認、重複送信、情報漏えい、複数端末・競合を確認する。

## 成功基準と禁止事項
- ケースごとに期待値、実コード結果、人間店長の入力、監査結果、回帰テスト成否を記録。
- テスト環境の設定点検、実LINE送受信、本番公開は別ゲート。人間役が参加しただけでは実LINE接続の証拠にならない。
- テスト中は本番LINE顧客へ送信しない、本番D1/KVを書き換えない、mainを更新しない、架空データを実カルテに入れない。
- 店長の実際の操作感は本人/店長からヒアリングして別に評価する。
