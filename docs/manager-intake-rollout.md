# 対象付き店長通知・AI聞き取り（テスト専用）

## 店長の操作

通知の「この注文を確認」を押すと、その通知に対応する注文と最新の返信案を表示します。押しただけでは送信しません。その後「1：送信」「2 修正した文章」「3：保留」で判断します。注文の名前・商品・数量・受取日時・方法・予算を併記します。通知のボタンに内部IDを保持しますが、トーク表示へは出しません。

古い版・処理済み・別の店長宛の通知は処理せず、最新の一覧へ案内します。同じボタンイベントが再配送されても、新しく選んだ注文へ選択を戻しません。店休日変更の途中で有効な注文ボタンを押した場合は、営業日変更を実行せずに注文確認へ移ります。

LINE公式のクイックリプライはiOS/Androidで表示されます。PCでは「返信待ち」→注文の番号→操作の番号を引き続き使えます。仕様参考：[LINEのクイックリプライ](https://developers.line.biz/en/docs/messaging-api/using-quick-reply/)。

## AI聞き取りの範囲

初期状態は無効です。次のすべてを満たす場合だけ、確定前の不足情報の質問を自動送信します。

- `ORDER_ENGINE=v2`
- `MANAGER_TEST_MODE=true`
- `MANAGER_AUTO_INTAKE_ENABLED=true`
- 対象顧客が `MANAGER_TEST_CUSTOMER_IDS` に明記されている
- 店長判断の理由がなく、質問が残っている
- 変更承認待ち・電話や店頭対応後の確認待ち・確定済み項目がない
- 制作の状態が相談中で、日付の解釈も曖昧でない

画像、以前の注文の照合、配達可否、緊急・苦情・支払い・変更などは自動対応しません。必要事項が揃った段階も店長確認へ回します。AIの聞き取りは価格・納期・受注の確約ではありません。

自動返信も注文の版チェック、許可送信先、送信待ち、同じキーによる再試行、会話履歴と監査記録を通ります。質問のために店長へ承認通知を送りません。手動修正で除いた質問は、質問済みとして記録しません。

## 公開手順

1. 対象がテストWorker・テストD1・テストKVであることを確認する。本番のチャネル設定は変更しない。
2. D1 migration `0018_manager_message_payload.sql` をテストDBへ適用する。追加列とボタン操作の重複防止テーブルが必要。旧Workerを動かしたまま適用できる追加変更。
3. `MANAGER_SEND_PAUSED=true` のままテストWorkerを公開し、署名・認証・許可リスト・DBスキーマを確認する。
4. テスト顧客だけを許可し、必要に応じ `AI_DISCLOSURE_ENABLED=true` と自動聞き取りフラグを有効にする。安全確認後にテスト環境の送信停止を解除する。
5. 実LINEで不足情報の質問→店長通知→ボタン選択→承認→顧客返信を確認する。古いボタン・複数注文・同一人物の二役も確認する。

自動聞き取りを止めるには `MANAGER_AUTO_INTAKE_ENABLED=false`。未試行の自動送信は取り消します。通信結果が不明な試行済み送信は、同じ本文とキーで結果を確定するため再試行を維持します。全送信を止めたい場合は `MANAGER_SEND_PAUSED=true`。通常の店長承認経路は自動聞き取りのフラグに依存しません。

テストリセットで返信案を削除する際は、関連する `manager_notification_events` を先に対象範囲だけ削除する必要があります。公式ナレッジ・本人情報・過去カルテを巻き込んで全消去してはいけません。本改修ではリセットを実行していません。

## 検証

`tools/test-line-e2e.mjs` は署名付き顧客受信、定期処理、自動質問、店長ボタン、明示承認、模擬送信まで検査します。`tools/test-manager-runtime.mjs` は例外・本番フラグ・許可外顧客・古い承認・再試行・停止を検査します。通信はモック、DBはメモリ上の新規DBです。実LINEでの合格とは区別します。
