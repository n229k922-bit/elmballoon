# 五つの運用事故対策

## 完了の意味

コードとローカル検証、テスト公開、実機確認、本番移行は別工程。未記録の電話・店頭・公式管理画面の送信を自動取得できたとは扱わない。絶対にエラーが起きないという保証はしない。

## 守る境界

1. 情報の鮮度：受信未整理、注文の版変更、手動対応の確認不足は古い承認を止める。手動で約束した内容はまず記録し、今回の注文へ紐付ける。失敗・不明な状態を送信成功として扱わない。
2. 全体負荷：営業日と制作・配達の余力は別。注文横断の予約枠を使い、上限・工数・対象日が不明なら許可しない。同時予約の上限超過をデータベースで拒否する。変更時は再確認し、取消は枠を解放する。
3. 承認範囲：返信送信の承認は制作可否・価格・注文確定の承認ではない。曖昧なOKは状態を進めない。注文の版と判断対象を結び付ける。既に送信を試した不明結果は同じ送信キーと本文で照合し、別本文で再送しない。
4. 過去情報：本人確認済みの記録だけを参考表示し、記録日・出典・未確定状態を残す。前回の価格、住所、好みを今回へ自動採用しない。検索候補の名前一致は本人一致ではない。
5. 運用評価：実イベント・質問送信・監査・送信結果から指標を算出する。未送信の質問を顧客負担に数えない。店長操作数は労働時間ではなく代理指標。受注率・利益・見落としゼロは記録から確認できなければ未測定とする。

## 検証と残る限界

### 店長操作

- 電話・店頭・公式LINEで別途対応したら「電話メモ M番号 内容」「店頭メモ M番号 内容」「手動対応メモ M番号 内容」。古い案を無効化し、返信・制作を停止する。
- カルテの必要項目を訂正したうえで「対応確認 M番号」。これは最新情報の確認であり、返信・価格・受注の包括承認ではない。返信は別途最新案を確認する。
- 「受付上限 日付 制作分数 配達件数 注文件数」で店舗全体の上限を設定する。
- 「受注枠 M番号 日付 制作分数 配達件数 注文件数」で当該注文の枠を確認。複数日はJSON配列で一括指定する。スマホ画面は制作日と受取日を分離する。
- 「負荷確認 YYYY-MM-DD」で登録負荷を確認。「運用確認」「改善状況」で直近7日の実記録を振り返る。
