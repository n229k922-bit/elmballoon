# 多様な顧客・クレーム・一名店長への集中検証

## 結論

通常の対象選択・重複受信・古い承認への防御は一部確認できた。一方、会話の意図判定・別注文・相談終了・苦情の継続状態・日時変更には不合格がある。現状を本番接客全体の合格とはしない。今回追加したのは検証基盤・合成ナレッジ・実装仕様で、受付本体の不具合修正やデプロイはまだ行っていない。

## 範囲

- 保存されている `REAL_CONVERSATION_KNOWLEDGE.md` の匿名事例を参照し、元見出しへ対応付けた。実個人情報・住所・連絡先は転記していない。過去全トークを今回再閲覧したという意味ではない。
- 20代から70代の男女24顧客。子供・母・父・同僚・卒業生・友人・恋人・店のママ・ホスト・団体などの贈答先を交差。即決、迷い、訂正、脱線、苛立ち、厳しい苦情、返金圧力を含めた。
- 性別・年齢から性格や好みを推測していない。相手の自己表明した希望と会話を応対の根拠とする。
- 24組×4発言＝96発言を、現行コードの共通メモリ内DBへ顧客交互に再入力。その結果を見た顧客役が次に送りたい訂正を24件追加し、同じ初期条件から5巡・120発言として再実行した。96+120を異なる216発言と数えない。
- 本体再入力には役割エージェントの店長判断を適用していない。役割応答、返信案、模擬送信、実LINE送信を区別する。
- 多様なケースの最初の4巡は脚本型。顧客役が実コード結果を見て作った追加1巡は応答依存の訂正である。完全自由会話を無制限に続けた試験ではない。
- 24例は代表的ケースであり、全組合せの網羅や実顧客満足度を保証しない。架空地域は実地域抽出の網羅性の証拠には使わない。

## 具体的な問題

1. EXP10：ブーケとスタンドが独立しない。EXP24：片方だけ見送りを扱えない。
2. EXP11：見送り後も商品質問を続ける。追加訂正でも改善しない。
3. EXP12〜14：取消・返金・破損苦情の文脈で通常の数量・予算等を聞く。
4. EXP20：旧受取31日と変更後18時が保存上合成される。顧客が訂正しても解消しない。
5. EXP01：赤を入れない希望が有効色に混ざり、訂正後も元の値が残る。
6. EXP04：今日中に返事を、という回答期限が受取日に影響する。
7. 安全事故・責任者への交代要求を通常注文確認から分ける仕組みが不足。

良い点もある。根拠のない受注・返金を確約しない、未照合履歴を具体的に開示しない、数量や否定された配送方法の訂正を扱える一部ケース、未処理の変更がある旧承認を送らない防御は確認できた。
