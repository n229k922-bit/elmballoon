# 三者会話による仮想ナレッジ

## 結果

顧客役6組・注文担当役・店長役を分け、顧客発言24件（4巡）、注文担当応答24件を保存した。顧客の隠れた希望と店長の架空の受付条件を相手役に先に見せず、公開された発言と判断を順に受け渡した。日付と価格は架空の前提であり、実店舗ルールではない。

- [出典付きナレッジ候補12件](knowledge-candidates.json)
- [実コードへのオフライン再入力結果](runtime-replay.json)
- 各役の振り返り：customer-feedback.json、clerk-feedback.json、manager-feedback.json

## 現行実装との照合

同じ6顧客・24発言を、共通のメモリ内DBと通信の模擬処理で現行の受付コードに再入力した。店長役の架空判断はこの実コード検証へ注入していない。LINE送受信、本番DB、公式アカウントには接続していない。

| 判定 | 再現内容 | 優先する対策 |
|---|---|---|
| 不合格・SIM-F01 | 文中の「あと別件なんですが」を別注文にできず、ブーケとスタンドの数量・予算・日時等が混ざる | 一通を注文別に分割し、独立した状態と承認対象を持たせる |
| 不合格・SIM-F02 | 「今回は見送ります」の後も注文の聞き取りが続く | 相談終了を先に判定し、同じ文の仕様訂正や次のお礼で自動再開しない |

上記は今回発見・記録した未修正の問題。仮想の注文担当が適切に返せても、現行システムが対応済みとは言えない。

## 再利用の境界

これはモデルの再学習ではなく、会話設計・改善・回帰テスト用の資料である。候補はすべて synthetic_needs_review / activation_allowed=false とし、実顧客カルテや本番ナレッジへ自動登録しない。既存の実会話インポートは変更していない。実価格・営業時間・配送範囲・予約可否の根拠には使わない。

資料の表示・出典検証に合格しても、業務フローの合格を意味しない。実LINEの受信→店長判断→承認→顧客返信は別途検証が必要。

## 再検証

リポジトリのルートから `node tools/replay-agent-dialogues.mjs` でオフラインの実コード再入力、`node tools/test-synthetic-dialogues.mjs` で保存資料の整合性を確認できる。後者は既知の問題が記録されていることも検査するため、成功表示を問題解消と解釈しない。
