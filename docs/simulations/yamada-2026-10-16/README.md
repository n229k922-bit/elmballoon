# 山田様の模擬注文：修正と実コード再生

2026-10-16。ベースmain: `432b225`。専用ブランチ: `codex/yamada-order-safety-20261016`。

## 修正した問題

- 予算と確定価格を分離。商品ごとの種類・個数・サイズ、税込総額、名入れ料金（無料なら明示0円）、可否、使用日と受取日時が揃わない提案は作成しない。
- 店長の具体提案は返信案として保存し、実送信済みの最新版に対する顧客の自然な「OK」「OKです」「はいお願いします」だけを承諾として扱う。未送信・別顧客・旧版・提案前の遅配発言・複数案件では勝手に反映しない。
- 承諾時に商品明細・税込総額・名入れ・日時をまとめてカルテへ反映。途中障害や更新競合時は元のカルテと別の確認待ち変更を保全する。
- 受取変更を依頼しただけでは旧予定を変えない。使用日の確認を後続発言でも維持し、提案文にも使用日を明記する。前日受取を使用日の変更と解釈しない。
- 使用日を先に質問し、相対日の回答を実際の質問履歴に結び付ける。「お店に伺います」、予算の「程度」「以内」、直前の名入れ質問への「NANO」、水色を保持する。
- 営業時間の質問を受取希望時刻として保存しない。時刻の項目確定でコロンを誤解析しない。
- 返信承認時と初送信直前に確約文を検査。通常の確認待ち文は通し、未確認の受注・価格・名入れ無料などの確約を具体提案の経路へ回す。
- 制作開始には具体提案と顧客合意の一致を要求する。予算の確認や単なる返信承認だけでは制作開始できない。了承後のお礼は合意を無効にしない。

`session.json` が顧客と店長の入力、`result.json` が実runtimeのカルテ・返信・模擬送信結果。店長判断を自動生成しない。`synthetic:true`必須、外部通信禁止、メモリDBと注入した模擬送信のみを利用する。入力の `@order:1`、`@draft:latest` は再生用の内部参照で、顧客に管理番号を入力させない。

再生で使う税込4,800円・名入れ0円・サイズ・在庫ありは、テスト専用の架空の店長判断である。実店舗価格・在庫・サービス条件として使わない。`sensitive-replay.json` と `manager-concurrency-results.json` は今回の再検証記録で、従来の修正前・前回修正後の記録は保持した。

## 店長向けの実装入口

`提案作成 M番号 {JSON}` で確認済みの条件を入力し、「返信待ち」で承認する。JSONは内部操作用であり顧客へ入力させない。必須キーは `items:[{type,quantity,size}]`、`total_yen`、`tax_included:true`、`personalization_fee_yen`、`feasible:true`、`receive_date`、`receive_time`、`use_date`、`fulfillment_method`、`balloon_message`（不要なら「なし」）。

顧客は送られた具体案へ自然な言葉で返答できる。既存の認証・送信制限・版確認を通し、名入れ・価格・受取の承認と制作・支払を区別する。

## 未実施・限界

- 本番・テスト公開環境の更新、実LINE送受信、実在庫・制作枠の照会はしていない。
- 新提案の作成は内部コマンド入口。フォーム化・スマホ操作の追加は未実施。
- 自由文の確約検査は決定的な表現検査で、すべての日本語を理解する保証はない。店長の入力根拠そのものを在庫システムと照合する機能もない。
- 前日受取の保管方法は、商品の実際の注意書きと構成に基づいて案内する必要がある。架空の耐久日数や保管保証は追加していない。
