# Lessons

- 店長メニューの「日付変更依頼」はHPの店休日・営業時間変更を意味する。お客様の受取日時変更とは別のシステム担当フローとして、変更内容の復唱と明示確定を挟む。注文日時や顧客送信は連動変更しない。

- 店長の確認待ち一覧は商品・数量・日時・受取方法と判断点を示し、英語状態・内部ID・架空サンプルを出さない。通常一覧からそのまま番号で確認できるようにする。

- 顧客向け確認待ちの文面は「お店で」など不要な内部主体を添えず、「対応できるか確認いたします」と自然に伝える。

- スマホの番号操作は「2本文」「２本文」「2 改行本文」を受け付ける。正規化は操作番号だけに限定し、お客様へ送る本文の全角文字・丸数字などは保持する。文面修正だけでは送信しない。

- 複数案件で省略操作を止めるだけでは店長が操作できない。固定した番号一覧→対象選択→返信案確認→承認まで一貫して用意し、選択と送信を区別する。確認コードは日本語に変換する。

- 店長の番号回答は通知の説明だけでなく受信処理まで実装・検証する。単一の有効返信案のみ省略承認し、複数案件・処理済み・更新済み案には番号のみで送信しない。

- 店長通知は判断に必要な注文内容・確認点・返信案・操作だけに絞る。内部列名、英語の保存値、通常の機械的期限、重複する管理番号は通知せずカルテへ残す。安全な対象指定は操作欄に保持する。

- 店長用スマホ画面は閲覧だけでなく、不足項目の追加と既存値の訂正までボタン操作で完結させる。内部コマンド入力を前提にしない。
- 通常ケースのテスト成功だけで安全とは判断しない。同一顧客の別案件が連続した場合と、状態遷移を飛ばす操作を回帰検証する。

- 顧客向け文面は初回案内・不足項目・回答確認の複数経路で生成されるため、変更時は全経路を同時に確認する。
- 日本語の日付は年の有無、和暦、R表記、区切り文字の揺れを前提に扱う。
- 店長向け操作は短い固定語にし、詳細は統括側の報告文へ集約する。
- 商品指定は画像だけでなく、HPの商品番号・丸数字・全角数字・「○番」表記を正規化して照合できるようにする。
- 商品マスター照合画像は店長・統括への内部通知だけに添付し、お客様向け返信と混在させない。
- 「未定で大丈夫」と案内する項目は、判定処理でも「未定」を回答済みとして扱い、同じ項目を再質問しない。
- 顧客メッセージの締め文を変更した場合は、複数メッセージへ分割する境界文字も同時に検証する。
- 全項目の回答をお願いする顧客向け文面では、内部の承認先を説明せず、正確でスムーズな案内に必要であることを伝える。「未定」「なし」を許容し、負担への配慮も添える。
- 自動返信は内容だけでなく応答速度も接客品質に影響する。短文・不足確認・長文復唱で待ち時間を分け、LINEのローディング表示と実際の遅延を一致させる。
- 店舗説明書をナレッジ化するときは、共通注意と商品固有注意を分け、資料にない耐久日数・返品補償を推測しない。破損相談は一次案内と店長通知を両立する。
- 顧客台帳と注文カルテは分離し、1人の顧客へ複数注文を紐づける。注文項目は値だけでなく、状態・回答元・質問回数・確定状態を持たせる。
- 制作可否の確認前は必要最小限だけを聞き、氏名・連絡先・商品別詳細・支払い・領収書は進捗に応じて後から埋める。
- 確定後の注文内容は直接上書きせず、新旧差分を店長へ示して承認後に反映する。
- LINEの分割送信は生ログを即時保存しつつ、返信判断だけを短時間まとめる。待機処理には世代番号を持たせ、最後の1件以外は返信しない。
- 注文開始・安全・破損返品・緊急連絡は会話統合の待機対象から外し、即時性を優先する。
- 店長の短文操作は対象が1件のときだけ省略形を許可し、複数ある場合は短いカルテ番号を必須にして誤更新を防ぐ。
- 注文完了は受渡しと支払いを別々に記録し、両方が確認できたときだけカルテを閉じる。
- 公式アカウント管理画面からの手動送信はWebhookで取得できないため、店長の顧客送信はシステム経由に統一し、送信・会話ログ・カルテ更新を同時に行う。
- 電話メモや店長送信から確定済み内容の変更を検出した場合は、送信または反映の前に新旧比較を表示する。1回の会話で複数項目が変わる場合は一括承認する。
- LINE公式アカウント管理画面から送った文はお客様への送信であり、顧客Webhookの受信トリガーにはならない。テスト案内では、個人LINEからテスト用公式アカウントへ送ることと、管理画面上の送受信方向を明記する。
- コピー用フォームでは、括弧内の例文・選択肢を回答として保存しない。ラベルと同じ行が空なら、説明行を除外したうえで次の実入力行だけを読み取り、未入力項目は必ず再質問する。
- 複数PCで同じ不具合を直した場合は、古いブランチの未コミット差分をそのまま重ねず、mainの改善意図を残して有効部分だけを移植する。
- 外部通知はコードの成功だけでなく、送信先ID・アクセストークン・配信結果まで監査する。送信先0件を成功扱いせず、失敗時は回数制限付きで再試行する。
- 顧客公式アカウントの受信通知と店長の判断通知は同じ内容を二重に送らず、顧客側は記録用・統括側は判断用として状態遷移単位に集約する。途中経過や照合結果は注文カルテへ保存し、緊急・承認が必要なものだけ統括へ送る。
- 店長向け返信案内に内部の `decision:` ID をそのまま表示しない。通常は「受ける／難しい／確認」の短文だけで処理し、複数案件のときだけ人が読めるカルテ番号を添える。旧形式のコマンドは互換性のため残す。
- リッチメニューの表示文言とWebhookの受信分岐は別物。固定テキストを追加したら、汎用フォールバックより先に専用コマンド判定を置き、各ボタンの初回案内と次の入力形式を実機で確認する。
- 統括や注文担当の新機能は、テスト用公式アカウントで入出力を確認してから実店舗アカウントへ移す。仕様作成・テスト実装・本番公開を別段階として扱い、公開許可を推測しない。
- 店舗営業時間と配達可能時間は別概念。10:00〜16:00の店舗対応時間を案内しても、夜間配達は地域・商品・当日予定の個別確認へ回す。
- お客様向け送信はAI案・店長指定文を問わず、送信案の表示と店長確認を必須にする。直接送信経路を残すと承認漏れが起きる。
- 来店・電話注文は顧客LINE IDが存在しないため、画像受信時に手動受付用の顧客・スレッド・注文カルテを合成し、元画像のLINE message_idと補足記録を紐づける。
- 長い正式番号を毎回入力させると操作ミスが増えるため、正式番号は記録用に維持し、確認待ち一覧の表示順に対応する一時的な1〜9の操作番号を別に設ける。
- 店長の短文入力は「操作番号→指示」の順を標準にすると視認性が高い。旧順序も正規化して互換性を保つ。
- 実店舗のリスクは一括で「対応可能」と扱わず、直前・配達・在庫・画像差・破損・予算・支払・紙注文・苦情・確認遅延を要注意フラグとして店長判断へ集約する。
- 決済は外部サービスの状態とカルテの状態を混同しない。AIは決済リンクやカード情報を扱わず、店長の確認操作だけで支払済みに進める。
- デプロイdry-runが成功してもD1本番スキーマが存在するとは限らない。公開前にremoteのmigration状態とテーブル数をread-onlyで確認し、権限エラーと未適用を別々に扱う。
- 外部APIの障害はエンドポイントを実際に叩いて初めて見つかる。Google OAuthのSecret名はコードとCloudflare一覧を突合し、接続済みKVだけで成功と判断しない。
- 商品未定のお客様へ全項目フォームを先に出すと離脱しやすい。初回は番号分岐にし、来店相談は希望日時だけ、商品・予算がある人は分かる範囲だけを受け付ける。
- 古い返信案の無効化だけでは手動対応後の矛盾を防げない。メモ保存後は最新情報の明示確認まで返信承認と制作を止める。
- 容量の集計は未登録・古い予約の注文をゼロ扱いしない。状態だけの版更新では枠を原子的に引き継ぎ、仕様変更では再確認する。
